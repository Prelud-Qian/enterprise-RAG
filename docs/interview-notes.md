# 面试口述笔记（RAG 项目必考题）

> 每道题：一句话结论（先说）→ 展开论证 → 本项目怎么做的 → 实测数据。口述控制在每题 1~2 分钟。

## 1. Chunk 分块大小如何权衡？过大过小的问题

**一句话：分块大小是「定位精度 vs 上下文完整度」的权衡。**

- **过大**（1000 字+）：一个块塞进多个主题，检索"命中"了但定位不准——相关的那句话只占块的一小部分，剩余全是噪声，白白消耗 LLM 上下文窗口；相似度分也会被无关内容稀释
- **过小**（100 字内）：语义被切断——"入职满一年享五天年假"可能被拆成两块，检索到哪块都答不完整；且块数爆炸，向量化成本、存储量、检索延迟全部上涨
- **本项目的做法**：500 字 + 50 字重叠作为经验起点（重叠解决边界处语义断裂）；在此基础上做 **small-to-big 两级分块**——500 字子块负责检索定位，2000 字父块负责喂 LLM，精度和完整度同时拿到；最后参数靠评测数据拍板（我的 30 条标注集 Hit@5=100%，分块参数对比实验可复现）
- 加分句：切分时优先按段落/句子边界落刀，比按字符硬切更符合语义

## 2. 为什么用 pgvector？对比 Chroma / Milvus 的优缺点

**一句话：百万级向量以内，pgvector 是"够用 + 运维成本最低"的选型。**

| | pgvector | Milvus | Chroma |
|---|---|---|---|
| 定位 | PG 插件，与业务库同库 | 十亿级向量专武，分布式 | Python 生态优先 |
| 运维成本 | **零新增组件** | etcd + MinIO + 多节点，重 | 独立服务，Java SDK 不成熟 |
| 亮点 | SQL 生态：事务/备份/JOIN，HNSW 近似索引 | 性能天花板高，GPU 加速 | 上手快 |
| 短板 | 单机性能上限（百万级够用） | 为中小规模付出整套中间件成本 | 生产案例少 |

- 加分点：我的隔离需求（知识库只能查自己的向量）在 pgvector 里就是一个 `WHERE kb_id = ?` 普通列过滤，专库还得靠 metadata 过滤；面试还能顺势讲清 `<=>` 余弦距离算子和 HNSW 索引原理（手写 SQL 而非框架封装）

## 3. 混合检索解决什么痛点？

**一句话：向量检索管"意思像"，BM25 管"字面像"，单用哪个都有盲区。**

- 向量盲区：口语与书面表达不同（"怎么涨工资" vs "调薪制度"），低频精确词（工号、编号、专有名词）向量表示学得不好
- BM25 盲区：同义词、改写、换个说法就召回不到
- 融合方式：两类得分量纲完全不同（0~1 相似度 vs 无上界 BM25），直接加权不可靠，用 **RRF 按排名融合**；融合后还有第二道 **Rerank 精排**（交叉编码器逐对打分）
- 实测数据：关键词精确型 / 语义改写型 / 否定句型三类提问全部命中，精排分 0.89~0.96

## 4. 如何抑制大模型幻觉？

**一句话：幻觉根源是模型在"没有依据"时被迫生成，抑制从工程、Prompt、数据三层做。**

- **工程兜底（本项目核心）**：检索质量阈值判断——最佳相似度低于 0.4 或无召回时，**直接返回固定话术，根本不调 LLM**。从源头掐断编造机会
- **Prompt 约束**：系统提示词强制"只依据参考资料回答，资料没有就明说没有"，temperature 0.1 降低随机性
- **数据侧**：检索质量本身就是防幻觉的第一道墙——混合检索 + 精排 + 父块完整上下文，喂给模型的每段都有据可查，还能溯源
- 测试证据：3 个库外问题（比特币/周边餐厅/薛定谔方程）全部拒绝回答，兜底话术一字不差（证明未经过 LLM 直接短路）

## 5. RAG 和微调的区别，为什么本项目不用微调？

**一句话：微调改的是"模型脑子里的知识"，RAG 给的是"开卷考试的资料"。**

- 微调：把知识写进模型权重。适合风格/格式/领域术语等**稳定能力**；代价是数据+算力成本高、知识更新要重新训练、还可能加重幻觉（模型把训练语料当事实硬答）
- RAG：知识放外部知识库，检索后注入上下文。知识**即插即用**（改制度=传份新文档）、可溯源、幻觉可控、天然支持权限隔离
- 为什么本项目不用微调：企业知识库的典型特征是**高频更新 + 强溯源要求 + 按用户隔离**——正是 RAG 的主场；微调适合做后续补充（如让模型固定输出公司报告格式）
- 面试金句：**RAG 管"知不知道"，微调管"会不会说"**
