## 评测方法

- **语料**：4 份仿真企业制度文档（员工手册/差旅报销/信息安全/绩效考核，各约 1100~1500 字，docx 格式），经 Tika 解析 → 两级分块（500/50，父块 2000）→ BGE-M3 向量化 → pgvector 入库，共 **8 个子块**
- **标注集**：30 条问题（`eval_set.jsonl`），每条锚定一个"答案所在块"（docId + chunkIndex），问题覆盖事实型（"试用期多久"）、多要点型（"密码有什么要求？多久换一次？"）、否定改写型（"杀毒软件能关吗？"）
- **判定**：调 `/api/kb/{id}/search`（完整检索链路：Query 改写 → 向量 + BM25 → RRF → Rerank 精排 → 父块展开），返回 Top-5 中存在标注块即判 HIT
- **工具**：`eval.py`（Python3 标准库） + `eval_set.jsonl`

## 标注过程中的发现（方法论笔记）

- 初版标注 3 条 MISS，排查后全部是**标注错误**而非检索错误：仅凭 120 字符的块预览判断条文落点，而分块在 500 字符处切断，部分条文实际落在相邻块。修正后 30/30
- **教训**：标注必须基于分块后的全量内容核对，不能凭"内容大概在第几段"推断；这也是分块参数变更后必须重跑评测的原因

## 局限与后续实验

- 语料为仿真数据且规模小（8 块 / 30 问），命中率高不代表泛化强；接入真实业务文档后重跑才有说服力
- 待做对比实验（切配置重跑即可）：纯向量 vs 纯 BM25 vs 混合检索、Rerank 开/关、不同 chunk-size 的 Hit@5 差异——这才是"参数怎么定的"的完整答案
- 耗时大头是 Query 改写 + Rerank 的两次 LLM 调用，延迟敏感场景可关改写（`rag.retrieval.query-rewrite.enabled: false`）或换更快的小模型
